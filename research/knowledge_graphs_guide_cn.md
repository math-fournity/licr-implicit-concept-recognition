# 中英文文本映射的知识图谱完整指南

对于构建同时处理中英文内容的文本-KG映射系统，**Wikidata是最强的基础**——提供1.15亿实体，完全多语言支持，CC0许可证。然而，最优覆盖需要组合多个KG：Wikidata用于通用知识，CN-DBpedia或OwnThink用于中文特定实体，ConceptNet用于常识推理，以及根据应用选择领域特定KG如UMLS或OpenAlex。

**关键发现**：中文KG的可访问性仍然具有挑战性——大多数高质量中文资源需要注册或学术机构背景，OwnThink是显著的例外，提供1.4亿三元组的免费下载。

## 一、大规模通用知识图谱

### 1.1 综合对比

| 知识图谱 | 实体数 | 三元组/事实 | 许可证 | 公开API | 中文支持 |
|---------|--------|------------|--------|---------|---------|
| **Wikidata** | 1.15亿 | 160亿 | CC0 | SPARQL | ✓ 完整 |
| **DBpedia** | 600-1000万 | 95亿 | CC BY-SA | SPARQL | △ 通过章节 |
| **YAGO 4.5** | 4900万 | 1.09亿 | CC-BY | 仅下载 | △ 通过Wikidata |
| **Google KG** | 540亿 | 1.6万亿 | 专有 | 有限 | ✓ 完整 |
| **Freebase** | 4400万(遗留) | 19亿 | CC-BY | 已废弃 | △ 有限 |

### 1.2 Wikidata（推荐首选）

**规模**：约1.15亿实体，160亿RDF三元组

**优势**：
- 语言中立的Q标识符，实现无缝多语言访问
- 实体同时具有原生中文标签和英文标签
- 全球社区实时更新
- SPARQL端点：query.wikidata.org（60秒超时）
- 每周JSON/RDF转储，CC0许可证允许无限制商业使用

**访问方式**：
```
SPARQL端点：https://query.wikidata.org/sparql
数据下载：https://dumps.wikimedia.org/wikidatawiki/
```

**适用场景**：通用实体链接、多语言应用、作为其他KG的锚点

### 1.3 DBpedia

**规模**：95亿三元组，覆盖111个语言版本

**优势**：
- 从Wikipedia信息框提取结构化数据
- 标准化的DBpedia本体：320个类，1650个属性
- DBpedia Live端点提供近实时更新
- 季度快照发布提供稳定性

**中文支持**：存在中文Wikipedia提取，但CN-DBpedia提供更深入的中文百科覆盖

**访问方式**：
```
SPARQL端点：http://dbpedia.org/sparql
中文端点：http://zh.dbpedia.org/sparql
```

### 1.4 YAGO 4.5（2024年发布）

**规模**：4900万实体，1.09亿事实

**核心优势**：**95%人工验证准确率**——开放KG中最高的质量保证

**特点**：
- 结合Wikidata实例与Schema.org清洁分类体系
- 通过OWL 2 DL约束确保逻辑一致性
- 无公开SPARQL端点，需下载本地部署

**访问方式**：
```
下载：https://yago-knowledge.org/downloads
```

**适用场景**：需要高准确率的应用、本体推理

### 1.5 专有巨头（参考）

| 系统 | 规模 | 访问限制 |
|------|------|---------|
| **Google Knowledge Graph** | 540亿实体，1.6万亿事实 | 有限API，明确警告"不适合生产关键服务" |
| **Microsoft Satori** | 20亿+实体 | 无批量下载，仅支持Bing内部 |

### 2.2 OwnThink（推荐入门首选）

**规模**：2500万+实体，1.4亿+三元组

**核心优势**：**最易访问的中文KG**——无需注册即可免费下载

**访问方式**：
```
API：https://api.ownthink.com/
GitHub：https://github.com/ownthink/KnowledgeGraph
数据下载：直接从GitHub获取
```

**特点**：
- 公开API支持实体消歧和知识查询，无需认证
- 融合了两千五百多万实体
- 亿级别的实体属性关系

**适用场景**：原型开发、学术研究、中文NLP入门

### 2.3 CN-DBpedia（复旦大学）

**规模**：1600万实体，2.28亿事实

**数据来源**：百度百科、互动百科、中文维基百科

**特点**：
- "永不停止"的提取系统，持续更新内容
- API免费（shuyantech.com），完整数据集下载需联系研究者
- Python库 `knowledgeworks_api` 简化集成

**访问方式**：
```
API：http://kw.fudan.edu.cn/
文档：联系复旦大学知识工场团队
```

### 2.4 XLore（清华大学）

**规模**：1490万实体，跨语言平衡

**核心优势**：**42.3万跨语言实体链接**——专为双语应用设计

**特点**：
- 显式双语设计，解决稀缺性问题
- XLore3与Wikidata 9200万条目集成
- 同时维护来自百度百科的专门中文覆盖

**访问方式**：
```
SPARQL端点：需申请
论文：XLORE 3: A Large-Scale Multilingual Knowledge Graph (ACM TOIS 2024)
```

### 2.5 OpenKG生态系统

**定位**：中国中央KG平台

**资源**：
- 122+数据集
- 54+工具
- cnSchema（Schema.org中文适配，链接到Wikidata）
- 领域特定KG：旅游、医学、教育

**访问方式**：
```
网站：http://openkg.cn/
注册：需要中文邮箱或微信账户
```

**关键工具**：
- **DeepKE**：知识抽取工具包
- **cnSchema**：中文模式定义

## 三、常识知识图谱

### 3.1 综合对比

| 常识KG | 规模 | 中文支持 | 特点 |
|--------|------|---------|------|
| **ConceptNet** | 3400万关系 | ✓ 62.5万断言 | 最强多语言常识 |
| **ATOMIC 2020** | 133万推理元组 | ✗ 仅英文 | 社会常识推理 |
| **SenticNet 7** | 20万概念 | ✓ 完整 | 情感知识 |
| **WordNet/OMW** | 11万同义词集 | ✓ 通过COW/CWN | 词汇语义 |
| **FrameNet** | 1200+框架 | △ CFN单独项目 | 框架语义 |

### 3.2 ConceptNet（推荐）

**规模**：3400万关系，304种语言

**中文支持**：约62.5万断言（主要来自台湾PTT宠物游戏众包项目）

**关系类型**（36种）：
- 物理推理：AtLocation, PartOf
- 社会知识：Desires, MotivatedByGoal
- 因果关系：Causes, HasSubevent

**嵌入**：ConceptNet Numberbatch包含600维中文向量

**访问方式**：
```
API：http://api.conceptnet.io/
下载：https://github.com/commonsense/conceptnet5
HuggingFace：conceptnet5数据集
```

### 3.3 ATOMIC 2020（Allen AI）

**规模**：133万日常推理元组，23种关系类型

**优势**：
- 社会常识（情感反应、意图、对他人的影响）
- 2020版本添加物理实体关系
- COMET-BART模型在常识生成任务上超越GPT-3

**限制**：**仅英文**，中文应用需要翻译或适配

### 3.4 SenticNet 7

**规模**：20万概念

**核心优势**：**专门的多语言情感知识**，完整中文支持

**特点**：
- 编码情感维度：愉悦度、注意力、敏感度、适应性
- Hourglass情绪模型实现细粒度情感推理
- 对情感分析和对话系统至关重要

### 3.5 关键缺口

```
仅英文的重要资源：
- ASER：4.38亿事件性（时间/因果推理）
- ATOMIC变体：社会推理

中文时间常识解决方案：
- 通过ConceptNet建立桥梁
- 翻译/适配英文资源
```

## 五、上层本体

### 5.1 综合对比

| 上层本体 | 采用度 | 特点 | 推荐用途 |
|---------|--------|------|---------|
| **Schema.org** | 4500万+域名 | 网络导向，JSON-LD | 实体类型化 |
| **BFO** | 350+本体框架 | 科学/生物医学 | 领域互操作 |
| **SUMO** | 2.5万术语 | WordNet映射 | 词汇语义推理 |
| **DOLCE** | 学术 | 认知语言对齐 | 研究 |
| **Dublin Core** | 数字图书馆标准 | 15个元数据元素 | 文档元数据 |

### 5.2 Schema.org（实践首选）

**采用度**：4500万+网站域名使用其标记

**规模**：797个类型，1453个属性

**优势**：
- Google、Microsoft、Yahoo、Yandex用于搜索结果增强
- JSON-LD格式，无严格本体约束
- YAGO 4.5使用Schema.org作为顶层分类体系

**适用场景**：实体类型化的实用选择

### 5.3 BFO（基础形式本体）

**采用度**：350+本体框架构建于其上

**设计**：故意最小化——仅35个类——最大化跨领域可重用性

**标准化**：ISO/IEC 21838-2确保长期稳定性

**适用场景**：如果系统处理生物医学内容，BFO对齐可实现与生命科学本体的互操作

### 5.4 中英文系统的实践建议

```
推荐组合：
1. Schema.org：用于实体类型化（最广泛采用，JSON-LD支持）
2. BFO对齐本体：用于需要互操作性的领域特定概念
3. Dublin Core：处理文档元数据
4. 自定义扩展：解决中文特定分类需求
```

## 六、LLM与KG集成

### 6.1 现代KG构建工具

| 工具 | 特点 | LLM支持 |
|------|------|---------|
| **GraphRAG** (Microsoft) | 社区检测+层级摘要 | 多后端 |
| **Neo4j LLM KG Builder** | 端到端提取 | GPT-4, Claude, Gemini, Llama, Qwen |
| **DeepKE** | 中文知识抽取 | 多模型 |

**GraphRAG**（2024，当前最先进）：
- 结合社区检测（Leiden算法）与层级摘要
- 支持本地和全局查询
- 开源实现，与Neo4j集成

**Neo4j LLM Knowledge Graph Builder**：
- 端到端提取，支持GPT-4、Claude、Gemini、Llama、Qwen
- 模式引导方法限制节点标签和关系类型
- 生产就绪的文本到KG管道

### 6.2 实体链接

**mGENRE**：
- 100+语言的最先进多语言性能（包括中文）
- 自回归生成方法直接产生Wikidata实体标识符
- 避免传统系统的候选生成瓶颈

**中文实体链接**：
- DBpedia Spotlight中文版
- MER-BERT-BiGRU：中文短文本89.73%精确率

### 6.3 知识图谱嵌入

**RotatE**（推荐）：
- 表达力和效率的最佳平衡
- 在复数空间中将关系建模为旋转
- 捕获对称、反对称和组合模式

**预训练嵌入来源**：

| 工具 | 覆盖的KG |
|------|---------|
| **OpenKE** (THUNLP) | Wikidata, Freebase, **XLore**（中文关键）|
| **LibKGE** | FB15k-237, WN18RR, YAGO3-10, Wikidata5M |
| **PyKEEN** | 30+模型，统一API |

## 七、构建中英文KG系统的建议

### 7.1 推荐架构

```
┌─────────────────────────────────────────────────────────────┐
│                     知识库层                                 │
├─────────────────────────────────────────────────────────────┤
│  主要：Wikidata（Q标识符作为语言中立锚点）                    │
│  中文补充：CN-DBpedia 或 OwnThink                           │
│  常识：ConceptNet                                           │
│  领域：OpenAlex(学术) / UMLS(医学) / 按需选择                │
└─────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────┐
│                     提取管道                                 │
├─────────────────────────────────────────────────────────────┤
│  工具：Neo4j LLM Knowledge Graph Builder                    │
│  中文LLM：Qwen                                              │
│  英文LLM：GPT-4 / Claude                                    │
│  模式约束：使用Schema.org类型                                │
│  后处理：实体聚类合并重复（KGGen方法）                        │
└─────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────┐
│                     实体链接                                 │
├─────────────────────────────────────────────────────────────┤
│  多语言：mGENRE → Wikidata                                  │
│  中文特定：CN-DBpedia mention2entity API                    │
│  本地索引：领域特定术语                                      │
└─────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────┐
│                     嵌入与存储                               │
├─────────────────────────────────────────────────────────────┤
│  嵌入：OpenKE的XLore嵌入（中英对齐）                         │
│  模型：RotatE                                               │
│  存储：Neo4j（Cypher，GraphRAG兼容）                        │
│  大规模：NebulaGraph / TigerGraph                           │
└─────────────────────────────────────────────────────────────┘
```

### 7.2 快速启动路径

```
阶段1：原型（1-2周）
├── OwnThink：免费下载，无需注册
├── Wikidata：SPARQL查询
└── ConceptNet API：常识补充

阶段2：扩展（1-2月）
├── CN-DBpedia：申请API密钥
├── OpenAlex：学术内容
├── Neo4j + GraphRAG：知识提取管道
└── mGENRE：实体链接

阶段3：生产（持续）
├── 领域特定KG整合
├── 自定义本体开发
├── 嵌入微调
└── 持续质量监控
```

### 7.3 关键洞见

```
核心发现：
1. 没有单一KG能全面覆盖两种语言
2. 成功需要深思熟虑地整合互补资源
3. OwnThink + Wikidata：快速原型的最佳起点
4. CN-DBpedia + 领域KG：随着覆盖缺口出现而扩展
5. LLM驱动的提取工具已足够成熟，可从非结构化文本构建自定义KG
```
